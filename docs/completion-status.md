## Release and upgrade rules

1. Keep storage identity stable. Evolve schemas and tested migrations instead of
   creating a new owner namespace for each release.
2. Run `pnpm check` and build the exact tree to deploy. The Web `build` runs checks before compilation; `verify:release` and `deploy` also require local-browser and reference acceptance.
3. Run local browser acceptance and the official-reference fixtures, then run
   deployed acceptance on the selected environment when provider/live behavior
   is in scope. Capture failures with their surface and transport; do not label
   a static roster check as rendered parity.
4. On an upstream pin change, inspect each fork, exported source entry, Host
   mapping, and disabled capability; update review commits only after review.

See [runtime ownership and limitations](runtime-parity.md) and the
[current Remote mapping](typed-remote-mapping.md) for the implementation boundary.
