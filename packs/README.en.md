# Capability groups

[简体中文](README.md) | English

Production rosters come from `scripts/composition/metadata-roster.mjs`: clients
use package metadata, `apps/web/composition.profile.json`, and pinned official
inventory; Worker/Think rows use package metadata. Application entries consume
generated rosters and must not hand-write feature lists.

`packs/<id>/pack.json` describes capability groups, dependencies, and owner
management scope for those plugins. It does not select production members.
`check:packs` independently parses packs and compares every row with production;
member, field, order, or disabled-state drift blocks release.

`packages/` defines where code lives and which runtime plane executes it.
`packs/` defines which plugins form a capability and which are owner-manageable.
For example, `waffo/pack.json` groups `@dsh-base/client-waffo` with
`@dsh-base/cloudflare-worker-payment-waffo` while preserving their plugin contracts
and runtime boundaries. A pack contains declarations, with no `src`, runtime
entrypoint or independent installation lifecycle. Deleting a pack does not
uninstall plugins or delete data; it fails the coverage check. Removing a
capability requires updating the actual plugin declarations and composition.
`requires` checks group references and dependency cycles; it does not replace
plugin `inject` contracts, service authorization or actual loading order.

- `planes.client` accepts package names (reading `dshBase.client`) or complete
  rows. `planes.worker` / `planes.think` accept package names, with loading
  contracts from `dshBase.worker` / `dshBase.agent` respectively.
- Prefer package-name references for local client plugins rather than duplicating
  IDs, module entrypoints, order and disabled state. Official profile rows and
  local rows with actual profile overrides retain full audit declarations for
  field-by-field comparison against production.
- Omit empty planes. Duplicate members, missing metadata, unknown dependencies,
  and dependency cycles are rejected.
- `requires` declares other pack ids.
- `toggleable: "L1"` is limited to bundled optional client/Think members; it may
  not contain required client plugins or Worker members. `none` means deployment
  management. L1 declarations remain the only source of owner-manageable modules.
- `reuse` records official candidates and the reuse decision. Forks must also
  record their provenance in the package's `dshBase.forkOf`.

For a new capability, first follow official reuse and declare the plugin and its
metadata/profile entries, then update its pack grouping. Run `pnpm check:packs`
and `pnpm check`. Generated rosters and L1 module lists are ignored outputs and
must not be edited by hand.

The Plugins page's complete owned inventory is generated by
`generate-owned-plugin-inventory.mjs` from the actual composition, independently
of the L1 management allowlist. Every independently registered client, Worker,
and Think plugin must appear in exactly one display group. Unregistered startup,
shared, or build packages do not become plugin entries. Disabled rows and
unavailable capabilities retain their declarations; actual Loader state remains
the source for live fibers, and the generator supplies no module resolvers.

`none` groups use the official bundle cards and component lists with read-only
controls. Gateway keeps one feature entry with two components; other existing
optional tools keep their own switches. A `dsh-base:<pack-id>` display identity
names a local composition group, not a registry-installable package. Existing L1
policy still governs mutations; increased visibility grants no new permission.
Run `pnpm plugin:owned-inventory` to generate data and
`pnpm check:owned-inventory` to check drift. Missing, duplicate, cross-plane, or
non-plugin members fail the check.

The plugin-management pack also includes the independent `@dsh-base/client-plugin-counts`. It uses an optional data slot in the marked official page fork to show category counts from the entries actually rendered, without additional service requests. Installed counts distinguish bundles from components; More includes the main experimental entries, so those counts must not be added together.

`global` groups site branding, public configuration, SEO, discovery resources,
public-page measurement and their settings interface under “Dsh-base Global”. The components in the [global pack manifest](global/pack.json) retain their
own runtime planes and loading declarations; grouping grants no permission to
change site configuration. Core features retain navigation, language,
permissions, and static assets; the disabled sidebar extras stay in that group.
Agent presets, model provider settings, attachment reading, and the unavailable
subagent belong to AI chat. Pack count, displayed bundle count and component
count measure different things: for example, optional tools in `optional-think`
are displayed separately, so directory count is not displayed bundle count.
Category counts always come from the actual inventory; run `pnpm check:packs`
and `pnpm check:owned-inventory` to verify them. Startup libraries, shared types
and data structures are not counted as feature plugins.
