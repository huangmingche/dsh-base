# Operational notifications

This Worker DSH plugin sends payment state updates to configured Discord and Feishu bot webhooks. The pinned official `dsh-webhook` and `dsh-webhook-github` packages accept inbound triggers and create Workspace-backed agent sessions; they cannot provide outbound delivery by adapting Host services alone. This plugin composes existing authentication, administrator policy and D1. It has no public message relay, queue, cron or always-on runtime.

Apply `schema.sql` to the existing `AUTH_DB` before enabling. Set `NOTIFICATIONS_ENABLED=true` and at least one secret `DISCORD_WEBHOOK_URL` or `FEISHU_WEBHOOK_URL`. Only exact HTTPS `discord.com/api/webhooks/{id}/{token}` and `open.feishu.cn/open-apis/bot/v2/hook/{token}` destinations are accepted; userinfo, query strings, fragments, alternate ports, arbitrary hosts and redirects are rejected. URLs are credentials and never enter public status, client bundles or the outbox. Missing or malformed configuration stays unavailable. Readiness does not probe the provider or schema. Bots must be authorized for the intended channel/group. Feishu keyword filtering can allow the fixed phrase `Payment update`; signature-protected bot configuration is not supported by this initial provider.

Waffo Pancake adds destination-scoped outbox statements to the **same D1 transaction** as order updates and verified event receipts. No receipt means no outbox insertion. Only material changes to plan, status, period, refund or supersession create notices. Repeated event deliveries and concurrent isolates share the same claim. An enabled missing outbox schema makes that financial transaction fail for provider retry; apply migrations before activation. If notifications are disabled, payment processing has no dependency on the outbox table and no notices are created retrospectively.

After commit, the request attempts pending deliveries, at most two channels in parallel. Each transport has a 10-second timeout and no redirect following. Discord uses `wait=true`, requires a message ID and disables mentions. Feishu checks the provider's business result code, including legacy `StatusCode`. HTTP rejection and explicit business errors become `rejected`; timeout, network error, 408/5xx, oversized or malformed responses become `uncertain`. A crash can leave `sending`. Provider acceptance is recorded as `accepted`, which does not promise exactly-once human delivery.

Accepted messages never automatically resend. Duplicate payment deliveries only flush still-pending records. There is no automatic retry for `rejected`, `uncertain` or `sending`. If delivery failed after financial commit, the payment remains confirmed. Administrators can investigate and explicitly retry; retries after uncertainty may duplicate a message. A stored destination fingerprint prevents an old record from being sent to a different webhook after a secret is changed. Retain outbox records for the required replay/audit window; deletion can permit a future duplicate if accompanying payment receipts are also deleted.

## API and service

- `GET /api/saas/notifications/status`: public `{enabled,ready,channels:{discord,feishu}}`, without URLs or secrets.
- `GET /api/saas/notifications`: authenticated `SITE_ADMIN_USER_IDS` administrator; returns the latest 100 `{id,channel,kind,orderId,state,attempts,createdAt,updatedAt}` records in `{deliveries}`. No payload, user email, destination URL/hash or token is exposed.
- `POST /api/saas/notifications/retry`: administrator, same configured origin, JSON `{id,expectedAttempts,reviewedUncertain?}`. A successful response means the attempt was processed; refresh the list to see actual provider acceptance. Accepted records always return 409. Stale attempts return 409. `sending`/`uncertain` require `reviewedUncertain:true`; `sending` also requires at least 15 seconds since its claim. Unknown or changed destinations cannot be retried.

Trusted plugins use `ctx.notifications.paymentStatements(env, notice)` only inside the matching Waffo Pancake receipt transaction, then `flush(env, eventKey)`. This is a typed payment-update service, not arbitrary message delivery. Messages contain event type, order ID, configured plan ID, current status and refund flag. They contain no customer names, emails, amounts or currency totals. Status/history APIs use `Cache-Control: no-store`; errors do not include provider payloads.

## Validation and source

Run `node --experimental-strip-types --test packages/cloudflare-worker/dsh-base-cloudflare-worker-notifications/tests/*.test.ts` and the Waffo Pancake `tests/runtime.test.mjs`. Tests use provider mocks and local workerd/D1, including atomic receipt/outbox writes, concurrent claims, uncertainty review, stale retry prevention, accepted-message replay and rollback on a missing outbox schema. No real Discord/Feishu messages or Waffo Pancake requests are sent.

The purchased TanStarter notification providers were reviewed for behavior, not copied. The implementation is independent and does not relicense the commercial template. Primary contracts: [Discord execute webhook](https://github.com/discord/discord-api-docs/blob/main/developers/resources/webhook.mdx) and [Feishu custom bot guide](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot?lang=en-US).
