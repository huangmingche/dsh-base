# Worker account authentication

This plugin uses Better Auth 1.7.18 and the existing `AUTH_DB` D1 database for product accounts, passwords and sessions. The official account stack provides DeepSeek OAuth and platform billing rather than local product authentication. The client seam continues to mount the official Account UI, with unavailable billing capabilities visibly disabled.

HTTP authentication requests use Better Auth's native `rateLimit.storage: "database"` with the `rateLimit` table already created by `apps/web/migrations/0002_username_password.sql`. Its conditional increments atomically consume a shared per-IP/per-path budget across Worker isolates and process restarts. There is no memory fallback or custom counter. This change adds no migration and changes no database identity, user ID or signing secret. Missing schema or D1 failures reject authentication instead of bypassing admission or issuing cookies. See [Better Auth rate limiting](https://better-auth.com/docs/concepts/rate-limit) for the database backend and the distinction between HTTP and internal API calls.

Only the `cf-connecting-ip` header overwritten by the Cloudflare edge is trusted; caller-supplied `X-Forwarded-For` is ignored. Better Auth normalizes IPv4 / IPv6 and shares IPv6 budgets by `/64` subnet. Username login, email login and enabled signup each allow 20 requests per minute; ordinary paths allow 600, and `get-session` allows 1200. Exhaustion returns 429 with `X-Retry-After`. This is persisted authentication-endpoint throttling, not account-wide protection against attacks from many source IPs, product API quotas or model spending limits. Internal `auth.api.getSession` calls bypass the HTTP limiter.

Registration is closed by default. Signup requires explicit enablement or the administrator provisioning token. Public `/api/auth-policy` exposes registration, email, verification, reset, Google and registered-extension capability flags without secrets. Cached instances are recreated when D1 binding, origin, secret, email configuration or extension revision/cache keys change, without modifying those settings.

Authentication reuses one session read within the same `Request` and environment. Each new request queries again, so a cross-request cache cannot retain revoked sessions. Internal permission checks disable renewal writes; actual authentication HTTP endpoints handle renewal that must return a Cookie. Database or authentication-service read failures return `503 auth_unavailable` instead of appearing as an anonymous `401`. Genuine guests and revoked sessions still cannot access private data. This fixes an error-classification path without claiming to establish the cause of earlier intermittent Staging failures.

A ready email plugin enables actual verification, resend and password-reset hooks. Only explicit `AUTH_EMAIL_VERIFICATION_REQUIRED=true` requires verification; required verification with unavailable email denies signup. Verification does not automatically sign in. Single-use reset tokens revoke previous sessions, and callbacks must be same-origin. Anonymous reset requests share a generic response. Bounded delivery runs after the response with Workers `waitUntil`, logging only a fixed failure event; request acceptance does not guarantee delivery. Reset requests and resends each allow 3/minute, reset submissions 10/minute. Upstream diagnostics that may include OAuth state are disabled.

`ctx.auth.registerExtension({id,cacheKey,options,policy?})` lets Worker plugins declare Better Auth plugins/socialProviders without overriding core security configuration. Duplicate extension/provider/plugin/policy keys are rejected. `handle(request,env,extensionId?)` retains origin, policy and HTTP throttling. Public native admin/API-key paths are denied; only corresponding internal scopes can enter wrapper endpoints. `invokeExtension` is restricted to registered plugin methods for trusted Worker services, without a generic HTTP RPC. Admin/API-key plugins own their schemas.

Native `/api/auth/update-user` is also closed. Profile writes must use account-profile's name and avatar ownership rules. Signup streams are limited to 16 KiB; JSON and form-encoded bodies both reject a client `image` field. Custom avatars use owned R2 files. Existing/official Google images remain intact, including during name-only edits. Optional email is read per request through pinned Cordis's documented `ctx.get()`; service identity changes invalidate cached auth hooks. `tests/composition-runtime.test.mjs` uses actual Cordis/static loader/workerd for startup without email, mail removal/remount, extension registration/disposal and resource cleanup.

`tests/email-google-runtime.test.mjs` uses actual workerd, Better Auth and D1 for mail tokens/sessions, OAuth state/PKCE, simulated token exchange, vendor redirect refusal and a successful callback. Local fixtures intercept mail and Google, with no external network or real delivery. Production providers require deployment acceptance.

Run `node packages/cloudflare-worker/dsh-base-cloudflare-worker-auth/tests/rate-limit.test.mjs`. Two actual local workerd isolates share persistent D1 to test exact concurrent admission, restart persistence, expiry races and pruning, IPv6 normalization, real signup / login / cookie sessions, and database failure denial. Tests use random secrets and a temporary persistence directory, with no deployed database or model access. `tests/policy.test.ts` additionally verifies closed registration, controlled provisioning, retired-account rejection and cached configuration updates.

## Public metadata routes

Auth uses the shared `@dsh-base/public-pages` resource registry for anonymous GET/HEAD navigations to sitemap, robots, manifest and llms, including HTML Accept. Manifest and llms support canonical locale prefixes. Exact resource matching grants no directory prefixes. Public metadata does not read account sessions; independent Worker producers and the missing-asset 404 guard own the response.

## Registration statistics hook

After Better Auth creates a real account, the optional siteAnalytics service receives sign_up. Its business key is hashed server-side; account details never reach Google. Google consent comes only from an explicit grant on that registration request. Without it, only configured first-party counting is allowed. Missing analytics or asynchronous failure cannot change registration outcomes.
